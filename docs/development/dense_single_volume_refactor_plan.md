# Dense single-volume refinement structural refactor

## Objective and scope

Refactor the production code under `relax/refinement` so its control flow,
data ownership and algorithm variants are easy to understand and change without
altering the refinement algorithm.

The production refactor stays in `relax/refinement`. Changes elsewhere are
limited to mechanical caller migrations, focused tests, diagnostic adapters and
documentation. Dense, local, sparse-pass and K-class numerical kernels are not
rewritten by this work.

This work must preserve score formulas, candidate generation, posterior support,
reduction order, dtype, random-number use, image order, M-step accumulation
order, convergence rules, RELION semantics, output quality, finalization,
compilation, buffer lifetime, memory use and runtime.

## Target ownership model

The intended flow is:

```text
RefinementRequest + resolved policies
                |
          initialize run
                v
       RefinementRunState
                |
       plan numbered iteration
                v
 DirectDensePlan | AdaptiveDensePlan | ExactLocalPlan
                |
          score each half
                v
        HalfScoreResult pair
                |
 fixed-order reconstruction and state updates
                v
       IterationResult / history
                |
      explicit final-pass plan
                v
         RefinementResult
```

Ownership rules:

- Requests and policies are frozen shallow containers. Their constructors do
  not cast, copy, synchronize or transfer arrays.
- `RefinementRunState` is the sole mutable owner of evolving maps, noise,
  priors, poses, corrections, convergence state and history.
- Helpers receive the smallest cohesive request or substate, not the whole run
  state as a service locator.
- Results retain the existing array objects, layouts and precision. Creating a
  result must not extend device-buffer lifetime unintentionally.
- Request objects remain outside JIT boundaries. Numerical kernels receive the
  same dynamic arrays and static arguments in the same order.
- Direct dense, adaptive coarse-to-fine, exact local, first-iteration CC,
  K-class and final all-data execution remain explicit variants.

## Acceptance targets

- No production function has 20 or more parameters.
- Prefer no production function with 10 or more parameters. Any remaining
  exception must be a documented functional/JAX boundary with a focused test.
- Production line totals are reported after every package. The final total
  should not exceed the initial total without a responsibility-level
  explanation; line reduction never justifies compressed or hidden flow.
- The main controller contains only entry validation, phase sequencing and
  explicit state transitions.
- Main controller and scoring orchestration contain no direct environment
  parsing. Document any infrastructure exception whose read timing is part of
  current behavior.
- Maintained output fields and serialized layouts remain unchanged even if the
  in-process result API becomes typed.

## Work packages

### 0. Metrics and characterization

Add the reproducible structural report and checked snapshot. Characterize each
execution route's selection, engine-call arguments, array identity, dtype,
error order, update order and result keys. Replace source-text tests that block
safe code movement with behavioral or AST ownership checks.

### 1. Cohesive request, state, policy and result contracts

Introduce small contracts for initial inputs, model state, iteration plans,
accumulator layout and run/iteration results. Migrate maintained callers in the
same package and remove superseded APIs rather than keeping two permanent
interfaces. Constructors remain shallow and host-only.

### 2. Half-scoring requests and explicit variants

Replace the 63-, 55- and 48-parameter interfaces and dictionary-based scoring
plans with a common per-half context plus explicit direct-dense,
adaptive-dense, exact-local and first-iteration-CC plans. Scorers return owned
result objects instead of mutating caller-owned result lists. Preserve the two
halves' independence and overlap behavior.

### 3. Environment and instrumentation boundary

Classify every environment read as production policy, resource policy,
diagnostic capture, replay intervention or experiment. Provide typed policy or
diagnostic objects at the same semantic boundary where each value is currently
read. Disabled instrumentation neither inspects nor retains arrays. Preserve
existing import-time versus call-time evaluation and isolate unavoidable
temporary environment mutation in a diagnostic adapter.

### 4. Initialization and iteration planning

Extract run validation, initial references and grids, replay application,
current/coarse-size planning, sampling transitions, perturbation and route
selection. Planning is host-only and produces an immutable iteration plan.
Preserve RNG access, candidate order, replay mutation order and convergence
latching points.

### 5. Numbered-iteration execution and state updates

Give half scoring, accumulator lifetime, low-resolution joining, FSC/tau2,
reconstruction, noise/normalization/scale updates, pose publication and
convergence mutation clear owners. Preserve their current sequence, including
previous-map release, accumulator offload, unregularized diagnostic maps and
cache-clearing boundaries.

### 6. Final all-data iteration and result assembly

Keep the final all-data pass separate from numbered iterations. Its reference
selection, joined accumulation, whole-data FSC/tau2 conversion, resolution
update, gridding and outputs have distinct semantics. Share only pure builders
whose identical calls, layouts, dtypes, failure order and fixed-state results
have been demonstrated.

### 7. Cleanup, documentation and final qualification

Remove transitional containers, forwarding layers, kwargs dictionaries and
proven duplicate assembly. Update the codebase, implementation and algorithm
maps and record final structural metrics.

## Equivalence rule for consolidation

Two implementations may be consolidated only after a focused comparison shows:

1. identical selected inputs and engine arguments;
2. identical array identity/aliasing, shapes, layouts and dtypes;
3. unchanged RNG, image, candidate, dispatch and reduction order;
4. unchanged error and fallback ordering;
5. unchanged buffer release, host offload, donation and JAX dispatch boundaries;
6. agreement in the applicable fixed-state replay and trajectory tests.

Otherwise the variants remain separate and receive names that explain why.

## Validation

For each production package, run its focused tests, `pixi run
test-em-fast-guard`, and `pixi run test-smoke`, recording the test receipt and
GPU model. At frozen milestones, compare fixed-state scores, support,
posteriors, poses, accumulators and update state against an immutable control.

Compilation checks record static arguments, executable/compile counts and cold
versus warm behavior. Performance checks use sequential control/candidate pairs
on the same physical GPU and record GPU memory, host RSS, compilation, warmed
compute and end-to-end wall time. The existing 10% regression-warning policy
applies.

Because the completed refactor spans every dense/local controller route, final
qualification runs `test-medium` and then the Slurm-only `test-long` milestone.
It requires unchanged convergence/finalization decisions, existing FSC gates,
and complete K1 and exactly-K4 results. Tolerances and committed scientific
baselines are never changed by this work.
